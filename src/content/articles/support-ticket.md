“不能用，快帮我处理”表达了着急，却缺少支持人员定位问题需要的条件。一个有用的工单，应让对方知道失败发生在哪里，以及你期待确认什么。

这套方法用于自己的订单与设备，不要求公开账号凭据，也不能保证商家的回复时效或退款结果。

## 先用一句话定义问题

把“所有都不行”缩小成可观察的动作，例如：“今天 20:10，在家庭 Wi-Fi 上，客户端更新订阅返回 403；旧配置打开普通网页正常。”这里同时给出了时间、网络、失败阶段和正常对照。

如果实际是付款问题，写“订单显示已支付，但账户套餐仍未激活”，而不是“机场故障”。网络与账单分开提交，方便交给负责的人。

## 五类信息，比十张截图更有用

| 信息 | 应提供什么 | 避免什么 |
| --- | --- | --- |
| 条件 | 系统、客户端版本、网络类型 | 只说“最新版本” |
| 时间 | 准确时间与时区 | 没日期的“刚才” |
| 动作 | 一个可以重复的操作 | 一次描述多个无关问题 |
| 结果 | 准确提示与正常对照 | 只贴无上下文大日志 |
| 请求 | 要确认的原因或下一步 | 要求客服猜测你的目标 |

平台无法复现你的本地网络时，记录仍能帮助判断问题范围；不要因此将家庭地址或公网 IP 随意贴到公开页面。

## 假设工单：把一句抱怨变成一条线索

原描述是“导入了还打不开”。进一步检查发现：配置已经保存，当前仍选择旧配置，目标应用没有重新验收。

更有效的描述是：“软件内有 A、B 两份配置；B 显示今天更新，当前标志仍为 A。我想确认怎样选择 B 并检查实际生效状态。附遮盖后的状态截图。”这条工单聚焦界面操作，不会误导支持先去查付款或服务器。

如果不清楚失败阶段，先读[订阅导入五阶段](/guides/subscription-import/)；连接后任务失败则读[连接排查](/guides/connection-troubleshooting/)。

## 连接问题模板

~~~text
主题：[客户端名称] [失败阶段] [开始时间]
系统 / 客户端与准确版本：
网络类型 / 时间与时区：
配置代号 / 代理方式（不含订阅）：
要完成的一个动作：
实际结果与错误提示：
普通网络基线与其他正常任务：
已尝试的单项对照 / 结果：
附件：已遮盖截图或必要日志片段
希望确认：下一项应检查什么？
~~~

只写确实做过的检查，不为了让表格完整编造结果。对方建议改变设置后，记录改变了什么并重复同一任务。

## 账单与优惠问题模板

~~~text
主题：[订单状态] [下单时间]
订单编号：仅在正式私人工单内提供
套餐名称 / 周期 / 币种：
页面标价 / 优惠实际减免 / 费用 / 最终支付额：
付款时间与时区 / 当前订单状态：
账户交付状态与正式条款中的预期：
附件：遮盖敏感字段的必要凭证
希望确认：支付是否入账？交付或退款适用哪项具体条件？
~~~

不要重复付款来判断是否入账，也不要在公开评论里提供完整支付凭证。提前把结算信息整理好，见[付款前订单记录](/blog/purchase-checklist/)。

## 分享日志之前，先做遮盖

客户端日志可能包含订阅参数、访问 URL、账户或设备信息。只保留与复现时间相关的必要片段，遮住密码、令牌、二维码、邮箱、私人文档路径及第三方信息。

[Clash Verge Rev 官方日志说明](https://www.clashverge.dev/guide/log.html)介绍该软件的导出方式。按对应软件文档采集，不把别的软件目录当成通用路径。临时提高日志等级后，复现完成应恢复日常设置。

## 收到回复后，用结果继续对话

把对方建议拆成一次改变一项的操作。回复“按建议切换配置后，20:35 同一任务完成；退出后普通网络也正常”，比“好像好了”更可复查。

若建议没有效果，补充新结果而不是反复发送同一段话。如果涉及条款，要求指明适用的正式条款和条件；第三方价格资料不能替代商家的订单承诺。保持同一工单记录，便于追踪上下文。

## 暂时没有回复，可以保留什么

保存正式工单编号、提交时间、订单状态和最近可用配置记录。是否继续使用、停止续费或申请退款，应按真实需求与正式条件决定；本文不假设任何品牌一定在某个时间内处理。

完整检查路线见[15 篇阅读路线](/reading/)，可以从你的失败阶段直接开始。
